# Тесты и критерии готовности

## Уровни
Unit (Vitest), интеграционные с реальной PostgreSQL в контейнере, e2e (Playwright), проверки доступности, оценки качества ИИ.

## Обязательные негативные тесты (напрямую по API и Server Actions, без интерфейса)
- Запрос без входа отклоняется.
- Наблюдатель (`viewer`) не может создавать и изменять.
- Менеджер (`manager`) не меняет и не удаляет чужие записи; не назначает ответственных; не видит чужие записи, если `manager_sees_all_readonly` выключена.
- Менеджер не запускает импорт и не выполняет слияние записей.
- Руководитель (`head`) не управляет пользователями, ИИ и не выполняет окончательное удаление.
- Не‑администратор не открывает настройки пользователей, ИИ, приватности.
- Нельзя удалить или понизить последнего администратора.
- Смена роли действует на следующем же запросе.
- Удаление контакта по запросу убирает персональные данные из всех таблиц, включая журнал.
- ИИ не вызывает инструмент и не возвращает данные, на которые у пользователя нет права.
- При исчерпании месячного бюджета ИИ он отключается, остальная CRM работает.
- Приложение не делает запросов к хостам вне списка разрешённых.

## Тесты дубликатов и слияния
- Нормализация: ИНН с пробелами и дефисами, email в разном регистре и телефон в форматах «8 (912)…» и «+7 912…» дают одно значение.
- Импорт помечает совпадение с существующей записью и дубликат внутри файла; действие «пропустить» ничего не меняет; «обновить только пустые» не затирает заполненные поля; «создать как новую» создаёт запись.
- Повторный импорт того же файла не создаёт копий при выбранном действии «пропустить».
- Слияние переносит сделки, контакты, задачи и заметки на основную запись, мягко удаляет вторую, пишет событие в аудит без значений персональных данных; при ошибке в середине откатывается целиком.
- Слияние недоступно ролям `manager` и `viewer`.

## Тесты отчёта «Продажи по менеджерам»
- Числа совпадают с эталонным набором сделок (выигранные, проигранные, открытые, доля выигранных).
- Суммы по разным валютам не складываются и показываются отдельными значениями.
- Менеджер получает только свою строку, даже если подставить чужой идентификатор в запрос.
- Фильтры по периоду, воронке и ответственному работают; экспорт CSV совпадает с таблицей.
- Мягко удалённые сделки не попадают в отчёт.

Тесты матрицы прав генерируются из таблицы `roles.md`: для каждой роли и действия проверяется разрешение и отказ.

## Критерии готовности задачи
- Есть тест на положительный и отрицательный сценарий.
- Нет обращения к Prisma вне DAL и репозиториев.
- Изменение пишет событие аудита без значений персональных данных.
- Есть состояния загрузки, пусто, ошибка, нет прав.
- Новая переменная окружения описана в схеме и `.env.example`.
- Миграция проверена на чистой БД.
- Нет внешних сетевых обращений кроме разрешённых адаптеров.
- Проходят `pnpm lint`, `pnpm typecheck`, `pnpm test`.

## CI на каждый pull request
Установка по lockfile → сканирование секретов и зависимостей → форматирование, ESLint (границы пакетов), TypeScript → unit → проверка миграций на чистой БД → интеграционные → Playwright (основной сценарий) → оценки ИИ (если менялись) → сборка и Docker‑сборка.

## Целевые показатели (ориентиры, подтверждаются нагрузочным тестом на объёмах из `capacity.md`)
Список до 500 мс на сервере при 50 000 записей; обычная операция до 800 мс; отчёт по менеджерам до 2 с при 50 000 сделок; предпросмотр импорта 8 000 строк с проверкой дубликатов в фоне, без блокировки интерфейса.
