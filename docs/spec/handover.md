# Передача заказчику

Результат работы — установка на сервере заказчика, которую он может запустить, обновить и восстановить по документации без участия разработчика.

## Состав передачи
1. Метка релиза в репозитории (`v1.0.0`) и собранные образы Docker (архив для загрузки без интернета, а также в реестре заказчика, если он есть).
2. `infra/compose`, `.env.example` и скрипты `install.sh`, `update.sh`, `backup.sh`, `restore.sh`, `healthcheck.sh`, проверенные на чистой машине.
3. Исходный код: репозиторий или архив с историей. Объём передачи и права определяются договором.
4. Документация: руководство администратора, руководство пользователя, инструкция по развёртыванию и обновлению, инструкция по восстановлению из бэкапа, runbook типовых сбоев, описание функций 152‑ФЗ (`privacy-152fz.md`).
5. Список зависимостей с лицензиями и SBOM.
6. Акт приёма‑передачи.

## Правила
- В репозитории и истории нет секретов, реальных паролей и данных заказчика. Секреты генерируются при установке и принадлежат заказчику.
- В production нет демо‑данных и учётной записи по умолчанию. Первый `admin` создаётся при установке.
- Доступы разработчика к серверу временные. После передачи они отзываются, пароли и ключи меняются.
- Развёртывание выполняется на аккаунтах и серверах заказчика, не на ваших.
- Установка не обращается к внешним ресурсам, кроме разрешённых заказчиком (почта, ИИ‑провайдер).

## Проверки перед актом
- Установка с нуля на чистом сервере по инструкции выполнена человеком, который не писал код (например, ИТ‑подрядчик заказчика).
- `restore.sh` восстанавливает тестовую копию, данные совпадают.
- `update.sh` обновляет с предыдущей версии на текущую и откатывается при ошибке.
- Тесты проходят на целевом окружении: вход всех четырёх ролей, импорт CSV, Kanban, отчёт по менеджерам.
- Мониторинг и оповещения о диске, очереди, бэкапе включены.
- Резервное копирование запущено, первая копия проверена.

## Задачи (в конце очереди)
- Задача 23: сборка релиза — метка версии, архив образов, SBOM и список лицензий зависимостей, проверка отсутствия секретов в истории, документы из раздела «Состав передачи».
- Задача 24: скрипт приёмочной проверки на целевом сервере (`infra/scripts/acceptance-check.sh`): healthcheck, вход под каждой ролью через API, создание и удаление тестовой записи, проверка бэкапа и восстановления в тестовую базу, отчёт в текстовом файле.
