# AGENTS.md — правила для ИИ‑агента

Проект: web‑CRM (B2B), заказная разработка под одного заказчика, self‑hosted на его сервере в РФ. Одна установка = одна организация (single‑tenant). Лицензирования и биллинга в коде нет. Подробные требования лежат в `docs/spec/`. Читай только файлы, указанные в задаче. Если требования нет в спецификации — задай вопрос, не придумывай.

## Стек
Node.js LTS, pnpm workspaces, Turborepo, Next.js App Router, React, TypeScript strict, Tailwind + shadcn/ui, Zod, React Hook Form, TanStack Table, PostgreSQL + Prisma, pg-boss (очередь в Postgres), MinIO, Vitest, Playwright.

## Роли
Четыре: `manager`, `head`, `admin`, `viewer`. Матрица и ключи прав — `docs/spec/roles.md`. Проверяй право (`ресурс.действие`), а не название роли.

## Жёсткие правила
1. Prisma импортируется только в `packages/db` и в репозиториях `packages/dal`. Больше нигде.
2. Права проверяются в `packages/dal` на каждой операции чтения и записи. Проверки в layout, middleware и скрытые кнопки — только UX, не защита.
3. Каждый Server Action и Route Handler: Zod‑валидация входа, проверка аутентификации и прав внутри.
4. Клиенту отдаются только DTO, не объекты Prisma.
5. Запрещены `any`, неисчерпывающие `switch`, файлы `utils.ts`, `helpers.ts`, `common.ts`.
6. Один файл — одна ответственность. Публичный API пакета — через `index.ts`; импорт вглубь чужого пакета запрещён.
7. Домен (`packages/domain`) не зависит от Next.js, Prisma и ИИ‑провайдера.
8. Деньги — `numeric`, время — `timestamptz` (UTC), валюта — код ISO.
9. Миграции только через `prisma migrate`. `db push` в production запрещён.
10. Никаких внешних сервисов и сетевых ресурсов: ни CDN для шрифтов и скриптов, ни облачного Sentry, ни аналитики, ни зарубежных API для данных. Шрифты и иконки — локально. Новую зависимость сначала обоснуй.
11. Секреты только из переменных окружения. Новая переменная = схема в `packages/config/src/env.ts` + `.env.example`.
12. Персональные данные не пишутся в логи и в журнал аудита как значения (маскируй).
13. Каждое изменение сопровождается тестами: положительный и отрицательный сценарий (отказ без входа, без прав).
14. Не кэшируй страницы и запросы с персональными данными без ключа, включающего пользователя.
15. Не добавляй лицензионные ключи, ограничения по тарифу и блокировки по числу записей или пользователей: объёмы из `capacity.md` — ориентиры для проектирования.

## Как работать
- Одна задача — один pull request. Не расширяй объём.
- Перед правкой прочитай файлы из задачи и существующий код рядом.
- В конце: `pnpm lint && pnpm typecheck && pnpm test`. Кратко перечисли изменённые файлы и что не проверено.
- Не меняй структуру репозитория, не добавляй пакеты без согласования.
- Не используй реальные данные: только вымышленные тестовые данные.
